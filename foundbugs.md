## Round 3 — safe-failure paths (audit of log_utils.guard / migrate error paths)

### MEDIUM

- [x] **#22 `SystemExit("message")` broke `guard()` and the `migrate --json` contract** — `log_utils.py:guard`, `migrate.py:load_components`. A `raise SystemExit(err(...))` from inside a library (the `--comp-dir` check) reached `guard`'s `except SystemExit` handler, which ran `int()` over the message: the user saw `Something went wrong: ValueError: invalid literal for int() with base 10: '<the real error>'`, `migrate --json --comp-dir <bad>` printed no JSON object at all, `profile_gen.py fill` crashed the same way, and `fetch_components.py --device <unknown>` buried its model list. FIXED: `guard` follows CPython semantics (int code = status, string = message printed then exit 1, `None` = 0); `load_components` raises `ValueError` (a library must not exit) which `migrate.cli_main` already turns into a clean line or the JSON error object, and `cmd_fill`/`cmd_propagate` catch that. Tests: `test_guard_survives_a_system_exit_message`, `test_unusable_comp_dir_is_a_clean_error_not_a_crash`, `test_empty_target_profile_is_a_clean_error`, `test_unknown_model_exits_cleanly_through_the_front_door`, plus the extra-arg case in `test_real_entry_point_propagates_the_exit_code`.

## Round 4 - dry-run honesty (cron audit, 2026-10-07)

### HIGH

- [x] **#23 The dry run counted sites a build does not write, and whole sections were invisible** - `cfw_builder.py:build_cfw` (dry-run branch). The dry run had its own entry loop next to the applier's: it printed entries that carry an offset without a value as patchable while `_apply_dict_patches` skips them, it never listed the `txm` section nor the nested `daemons` entries, and its section list was hardcoded. A count a user gates a restore on has to be the count a build writes, and a dry run that cannot see a section is worse than none. FIXED: `appliable_dict_entries()` is now the one filter shared by the applier, the plan and the tests; `dry_run_plan()` buckets every site as patchable / skipped (with a reason: pending sentinel, blocked section, another board's kernelcache component, daemon binary in the rootfs dmg, no offset+value) / unpatched section; `patch_userland` and the plan share `_daemon_binaries()` (one tree walk); the dry run prints the per-section counts, the skip reasons and any unapplied section, and logs a WARN summary; `cfw_builder.py <ipsw> <profile> --check-only` returns the build result, so a refused profile exits 1 instead of 0. Tests: `tests/test_cfw_builder.py` (15, incl. applier/plan parity and a synthetic IPSW tree that proves a dry run writes nothing).

- [x] **#24 The `txm` section is never applied by the build path** - `cfw_builder.py`. Every profile carries a `txm` section (iPhone12,1/12,3: 6 entries: query_module0/1/2, two constraint-signature no-ops, allowed_before_secure_channel). Those offsets are migrated, validated by `device_offsets.py validate`, byte-verified by `preflight.py` against the fetched `txm.raw` and imported by `liter8_import.py`, but no code path writes them: `cfw_builder.py` has no txm patcher (grep: the module never mentions txm). Upstream `usbliter8-fun/work-27.0b3/make_cfw.py:97-130` does extract `Firmware/txm.iphoneos.release.im4p`, patch `TXM.raw` and re-wrap it back into the CFW (`-f trxm --lzfse` plus the PAYP trailer fixup), and `research/work/audit_make_cfw_iPhone12,3_27.0b3.md` marks those 5 entries COVERED by that source. Impact: a CFW built by this toolkit carries no TXM patches at all. Real evidence after #23: `python3 cfw_builder.py research/extracted/iPhone121_27.0_24A437 offsets/iPhone12,1_27.0.yaml --check-only --force` prints `6 txm entry/entries are NOT applied: the build path has no patcher for this section` (before #23 it printed `Dry-run complete - all patches validated`). OPEN on purpose: adding the patch is flash-affecting (the rewrap has to mirror upstream, PAYP trailer included) and must go through a reviewed run against real components, so the dry run reports it instead of inventing a path.

  FIXED 2026-10-07: `cfw_builder.patch_txm()` resolves the device's `txm` component, extracts the payload, applies the profile's txm entries with the same applier as iBSS/iBEC, and rewraps into `<ipsw>/Firmware/<name>` keeping the container's own fourcc (`trxm`, read from the real iPhone12,3 24A5380h component) and Apple's description. The stage numbering grew to 7 (`4/7 Patching TXM`), txm is in `DICT_SECTIONS` so the dry run/plan and the applied set cannot drift, and a `blockers:`-marked txm section is refused even under `--force` (same rule as the kernel). Verified against the real component: `python3 cfw_builder.py research/extracted/iPhone123_27.0b3_24A5380h offsets/iPhone12,3_27.0b3.yaml` patches 6/6 txm sites, the output container unwraps to fourcc `trxm` + description `1` with exactly the 6 sites changed and every other byte identical. `--check-only` on that profile now prints `40 patch site(s) would be written, 8 skipped` with no "NOT applied" section (was 34 + "6 txm ... NOT applied"). Caveat, unchanged from the iBSS/iBEC path: our writer stores the payload uncompressed while upstream passes `--lzfse`, so the rewrapped container is bigger than Apple's; no PAYP trailer is added. Tests: `tests/test_cfw_builder.py` (txm sites applied through the applier, container shape kept, blocked section refused, missing component a clean skip).


## Round 5 — issue sweep (2026-10-07)

### HIGH

- [x] **#25 Site-dependent patch values were filled with the site's own instruction (no-op patches)** - `profile_gen.py:_discover_section`, `migrate.py:_update_entry`, `preflight.py:check_site`, `offsets/iPad12,1_27.0b3.yaml`, `offsets/iPad12,2_27.0b3.yaml`. An `adrp`/`add` pair has to point at a slot in *this* build and `keep_nonce_b`'s branch has to skip the nonce check, so their values are not derivable by pattern search: the only word the engine can offer is the one already at the target site. It wrote that word as the patch value, so the profiles claimed a redirect that never happens. Proof: both iPad b3 profiles carried `ibss.boot_args_adrp=62080090`, `ibss.boot_args_add=428c2f91` (and the same pair plus `ibec.keep_nonce_b=ceaf0194` in ibec) with `method: cross-device` and `pending: false` - every one of those values is byte-identical to the site in the real `iPad121_27.0_24A5380h` component, i.e. 5 no-op entries per profile that preflight called `already-patched` (a warning) and the builder would happily write. FIXED: `device_offsets.SITE_DEPENDENT_ENTRIES`/`is_site_dependent()` names them, the fill/propagate engine locates the offset but strips the value and keeps the entry `pending` with `SITE_DEPENDENT_REASON`, `migrate._update_entry` refuses a site-derived value (it keeps a profile's committed value and flags `value_needs_review`, printing the list at the end of a run), `preflight` gained a blocking `no-op` status for exactly this shape, and both iPad b3 profiles now mark those 5 entries `pending: true` with the reason (their `pending:` lists grew 2 -> 7). Verified: `preflight.py offsets/iPad12,1_27.0b3.yaml --components research/extracted/iPad121_27.0_24A5380h` = 10 verified / 0 bad / 7 unchecked (the 5 no-ops are gone, the entries are honestly pending); iPhone12,3 b3 unaffected (17 verified / 0 bad).

## Round 6 - safe failure on the write path (2026-10-07)

The theme: a build writes bytes a restore hands to a device, so "it usually works" is not good enough. Every one of these is a way the toolkit could have flashed something it could not vouch for.

### HIGH

- [x] **#27 `_patch_at` wrote past the end of a component and grew the payload** - `cfw_builder.py:_patch_at`. There was no bounds check: `fp.seek(offset)` + `fp.write(data)` past EOF writes at that offset and the file grows, so a profile offset that does not fit its component produced an image with a hole and appended bytes instead of an error. For iBSS/iBEC that is a container whose payload no longer matches its length fields, i.e. a corrupt image a restore would hand to the boot chain, and the build still printed "patched". FIXED: `_patch_at` measures the file and raises `PatchOutOfRange` (`0x… + N B is past the end of the 8,192 B component`), `_apply_dict_patches` counts such an entry as a failure and does NOT count it as written, and a section with any failure never publishes (it returns False before the rewrap, so the component on disk is the one Apple shipped). `PATCH_FAILURES` is the shared record; `_section_failed()` is what the patchers check. Tests: `test_patch_at_refuses_a_write_past_the_end`, `test_an_out_of_range_entry_fails_its_section_and_is_not_counted`, `test_a_section_with_a_failed_entry_never_publishes`.

- [x] **#28 Nothing verified what a build wrote to disk** - `cfw_builder.py:_wrap_raw_to_im4p`, all patchers. Encode and write was the whole story: if the container writer dropped the payload, swapped the fourcc, or wrote through a truncated file (crash, full disk), the tree still said `patched` and the manifest agreed. FIXED: every write goes through `publish_component()`, which encodes, writes atomically (temp file + `os.replace`), then calls `verify_component()` to re-open the file and prove it unwraps to exactly the patched payload with the original container's fourcc and description preserved (`_shape_of()` reads them off the bytes that are being replaced). On any mismatch the original bytes are restored (or the file this build created is removed), the section is marked `failed`, and `PUBLISHED` does not record it. Kernel and RestoreRamdisk go through the same path, and the rootfs daemons (patched in place, no container to rewrap) get `verify_binary()`: same size, every site holds its value, else the pre-patch bytes are written back. Tests: `test_a_published_component_reads_back_as_the_patched_payload`, `test_fourcc_and_description_of_apple_s_container_are_kept`, `test_a_component_that_does_not_verify_is_rolled_back`, `test_a_component_this_build_created_is_removed_when_it_fails`, `test_a_wrong_fourcc_is_caught`, `test_a_daemon_that_fails_its_check_is_put_back`.

- [x] **#29 A restore flashed whatever was in the work dir, and a partially applied build was reported as a success** - `boot_chain.py:restore_device`, `cfw_builder.py:build_cfw`. `restore_device()` erased the device after running the work dir's `make_cfw.py`, with no check that the tree those components came from still held the patches, and a build that skipped several sections printed the same green box as a complete one (only an extra warning line distinguished them). FIXED: the build writes `.ul8-build.json` (profile hash, every published component's sha256, per-section outcome, `fully_applied`), `cfw_builder.py <tree> <profile> --verify` re-checks those hashes plus the profile's sites and exits 2 on anything wrong, and `restore_device()` runs that check before stage 1: a tree that does not match its marker refuses to restore (`UL8_FORCE_RESTORE=1` is the deliberate override), a work dir with no marker says it cannot be checked, and a build whose sections were skipped now says `N section(s) NOT fully applied` in the summary and in the marker. `verify_tree` also refuses to let a stale duplicate pass: if the tree resolves a component that is not the one the build patched, that is a hard finding, because a restore would use bytes nothing verified. Tests: `test_the_marker_hashes_exactly_what_the_build_wrote`, `test_verify_tree_passes_a_tree_that_holds_its_patches`, `test_verify_tree_catches_a_component_changed_after_the_build`, `test_verify_tree_reports_what_it_could_not_check`, `test_verify_tree_flags_a_profile_that_changed_since_the_build`, `test_a_failed_section_keeps_the_tree_out_of_a_flash`, `test_restore_originals_drops_a_marker_it_invalidated`.

- [x] **#30 A build could resolve its own pre-patch backup as the component to patch** - `components.py:_is_payload`, `cfw_builder.py:_keep_original`. The originals store is a directory inside the tree (`.ul8-originals/Firmware__dfu__iBSS.d421.RELEASE.im4p`), so the next build's resolver - which walks the tree - could pick the BACKUP as the component to patch: it would write the patched bytes there, report `patched`, and leave the component the restore actually uses untouched. Same class of bug for the marker file. FIXED: `EXCLUDE_PARTS`/`_is_payload()` skip any path with a `.ul8` part, and the store is written with a name -> relative-path index so a root-level component (the kernelcache) and an out-of-tree one (the CFW iBEC, written to `<tree>/../CFW/Firmware/dfu/`) both restore to exactly where they came from. `--restore-originals` puts them back byte-identically and then deletes the marker, since the tree is no longer the built one. Tests: `test_the_originals_store_and_marker_are_never_resolved_as_components`, `test_restore_originals_puts_the_tree_back`, `test_restore_originals_reaches_a_component_outside_the_tree`.

### MEDIUM

- [x] **#31 An unparseable profile value ended the build with a traceback** - `cfw_builder.py:entry_bytes`/`_apply_dict_patches`. `device_offsets.hex_to_bytes()` calls `.replace()` on its argument, so a value that is neither a string nor bytes (a nested mapping, an int, null) raised `AttributeError`, which escaped `_apply_dict_patches` into `guard()`: the whole build died as "Something went wrong: AttributeError: 'dict' object has no attribute 'replace'" instead of the section reporting one bad entry. FIXED: `entry_bytes()` normalises the conversion (bytes pass through, hex parses, str falls back to ASCII for the boot-args style patches, everything else raises `TypeError`) and every caller - `_apply_dict_patches`, the kernel loop, `section_sites()`, `verify_tree()` - catches it and counts that entry as failed/uncountable rather than propagating. Tests: `test_an_out_of_range_entry_fails_its_section_and_is_not_counted`, `test_an_ascii_value_is_still_written_verbatim`.

- [x] **#32 `skipped` and `failed` meant the same thing to the summary** - `cfw_builder.py` patchers. A component that is simply not in this tree (no iBEC, no rootfs for the daemons, no DeviceTree in a partial extraction) was marked `failed`, so a perfectly reasonable partial tree made `ok_patch` false and the build announced "CFW build had errors" with no explanation, while the kernel/ramdisk sections already used `skipped`. FIXED: absent components are `skipped` with the reason, everywhere; the summary distinguishes `patched`/`partial` from `skipped`/`failed`/`mismatch`, the marker records `fully_applied: false` and the restore gate lists each skipped section. Nothing is hidden - a skipped section is still not applied, and it is printed as `N section(s) NOT fully applied` right above the tree path.
